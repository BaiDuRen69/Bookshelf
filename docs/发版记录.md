# 小书房 · 发版记录

> 本页是交付物的**机器可比对**台账，两条用途：
> 1. `scripts/pack.ps1` 每次打包后拿这里的**上一条可交付行**做 SHA-256 与体积（±5%）比对；
> 2. `tools/check_doc_drift.py` 把它当文档之一，比对 versionName / versionCode / DB / 单测数字。
>
> **一行 = 一个包 = 一个提交**：SHA-256 与「产出时 HEAD」必须一一对应，做不到就说明这一行不该进表。
> **数字只能是实测值**：体积与 SHA-256 由 `Bookshelf/tools/check_release_package.py --apk <文件>` 读出，
> 版本与 ABI 由 `aapt dump badging` 读出，日期取 APK 文件修改时间，HEAD 与工作区状态由 git 读出。
> 手写凭印象的数字不要进这张表。新行加在表格末尾，不要重排历史行；
> 交付目录里被判定「不可交付」的旧包也照实列出并标原因。

## 列口径（v5.9.6 起由脚本采集，之前为人工回填）

| 列 | 谁写 | 怎么得到 |
|---|---|---|
| 日期 / 文件名 | pack.ps1 | APK 文件修改时间 + `XiaoShuFang-v{versionName}.apk` 命名 |
| versionCode / versionName | pack.ps1 | `aapt dump badging` 的 package 行 |
| SHA-256 / 体积 | pack.ps1 | `Get-FileHash` + 文件长度 |
| 产出时 HEAD | pack.ps1 | `git -C <工程根> rev-parse --short HEAD` |
| 工作区 | pack.ps1 | `git status --porcelain`：跟踪文件有改动、或 `app/` 下有未跟踪文件 → 「不干净」 |
| 正式槽位安装 | 人工 | 装完正式版后 `adb shell dumpsys package com.bai.bookshelf`，取 `versionName` |
| androidTest 复跑 | 人工 | 整套仪器化测试是否在本包上跑过（跑过要写设备号；跑在 devtest / debug 构建上必须写明，那不等于本行的 release 包） |
| 判定 | pack.ps1 | 全部判据通过写「可交付」；否则列原因写「不可交付」 |

**工作区不干净时 pack.ps1 拒绝写入这一行**（v5.9.5 就是这种包：交付的是 38 919 971 B，
用当时的源码状态重建得到 38 965 063 B，两个数对不上，因为那批改动要到下一天才提交）。
这种包可以先自行核验、先装着用，但**不进这张表**；要进表就先把源码提交，用干净的树重建一次。

## v5.9.5 的归属问题（B4 的直接起因）

- 表里交付行：`f1c00c68…` / 38 919 971 B（2026-11-09 产出）。
- 2026-11-10 用工作区重建：`eb4e1ceac7aabda47446a311f78649cda0eb6324d3883aef9f2ee9a858009ab8` / **38 965 063 B**。
  两个包不是同一个产物，差 45 092 B。
- 结论：**这个 APK 无法归到任何一个提交上**——包里那批源码当天还没进仓库，而仓库里现在是提交之后的状态。
  按新口径这类包不进表；这一行是存量，保留只为让旧包可追溯，已在判定列点名。
- 下一次真正交付前要做的收敛：把 versionName / versionCode 抬到 **5.9.6 / 140**，在干净的树上重新打包，
  由 `scripts/pack.ps1` 自动写入新行（HEAD 与 SHA 一一绑定）。不要拿同号覆盖发布。

## pack.ps1 比对口径（重要）

- **SHA-256**：与「上一条**可交付**行」比。完全相同 → Fail（内容没变却重新发同号，或产物是旧的）。
- **体积**：相对「上一条**可交付**行」±5% 以内为 Pass，超出判 Fail 并说明差值。
  基准必须跳过不可交付行：5.9.5（37.12 MB）如果跟字面上一行 5.9.4（73.31 MB）比，会得到 -49.4% 的
  假告警；跟 5.9.0（37.05 MB）比才是 +0.19%。
- **扫描范围**：交付目录里全部 `XiaoShuFang-v*.apk` 逐个套同一判据，不能只判新产出的那一个——
  上一轮那两个 `.devtest` 包就是静静躺在交付目录里的例子。`Get-ChildItem` 不递归，
  所以 `归档-不可交付/` 与 `dist/历史/` 里的包都不参与扫描（2026-11-10 卡 G2 起交付目录默认是
  工作空间根的 `dist/`，历史包收进 `dist/历史/`；扫描只看 `dist/` 那一层）。
- **列位置**：解析按新表头取列（判定 = 第 11 列，SHA = 第 5 列，体积 = 第 6 列，文件名 = 第 2 列，
  表头行与分隔行按关键字自动跳过）。改这张表的列顺序时必须同步改 `scripts/pack.ps1` 的取列下标。
  2026-11-10 实测：用旧版脚本（9 列口径）读这张新表，基准一行也匹配不上，直接
  `[FAIL] 没有可解析的可交付行` —— 表和脚本必须同一次提交。
- **体积写法**：千分位只用空格（`38 965 063 B`），不要用逗号——基准解析的正则是
  `(\d[\d ]{4,})\s*B`，认空格认不出逗号，写成 `38,965,063 B` 会被静默跳过这一行。
- **写行**：全部判定通过且工作区干净时由 `scripts/pack.ps1` 追加新行（正式槽位安装 / androidTest 复跑
  两列写 `待填`，人来补）；工作区不干净只打印原因、不写行。同一 SHA 已在数据行里出现则跳过不重复追加
  （只比数据行，正文里引用的哈希不算登记）。补完记得跑 `python -X utf8 tools/check_doc_drift.py`。

## 命名口径

v5.8.33 及以前用 `小书房-vX.Y.apk`，v5.9 起统一 `XiaoShuFang-vX.Y.apk`（拼音，避免中文路径在
CI / 传输环节被搞坏）。老命名的三个包本身是可交付的 release 构建，只是前缀不在 `XiaoShuFang-*`
扫描口径内；交付目录清理时按「保留最新可交付 + 保留一个最近老命名样本」处理，删哪些由人决定。
2026-11-10 卡 G2 的处置：一个包没删，老命名的三个（5.8.31/32/33）连同 `XiaoShuFang-v5.9.0` 一起
收进 `dist/历史/`，只有 `dist/XiaoShuFang-v5.9.5.apk` 留在交付层；判定结果按 `check_release_package.py`
逐个数过——八个包里只有 5.9.5 判「可交付」，另外 5 个只输在「包内 versionName ≠ build.gradle 当前声明」
这一条（历史包本来就该输），真正内容不可交付的是 `归档-不可交付/` 里那两个 `.devtest` + x86 的包。

  **同时写明它跑在 devtest 槽的 debug 构建上**——本行这个 release 包一次没装过，不能读成「本包已复跑」。
- **正式槽位安装列**保持 `待填`：本轮未连真机采集，正式槽当前 versionName 属 UNKNOWN，不臆造数字。
