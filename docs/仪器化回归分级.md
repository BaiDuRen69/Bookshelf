## 1. 分类口径：判据是「决定性标记」，不是 import 计数

第一版分类用「有没有 `import android.*` / 有没有 `Context`」当判据，**当场判错两个文件**：

- `BatchImportTest`：不 import 任何 `android.*`，但它走 `BookshelfApp.get()` 拿全局 Application，再用真实 Room 写库 → 下沉不了。
- `LunarCalendarInstrumentedTest`：测试文件本身只 import `androidx.test`，看着像纯逻辑；但被测类 `LunarCalendarIcu` 用的是 `android.icu.util.{Calendar,ChineseCalendar,TimeZone}`（`LunarCalendarIcu.java:3-5`）→ 农历换算整个绑在平台 ICU 上，下沉不了。

所以判据改成**决定性标记**（命中任意一条即「真依赖 Android」）：

1. `ApplicationProvider` / `InstrumentationRegistry` —— 要 Context
2. `BookshelfApp.get` —— 要全局 Application
3. `Room.inMemory` / `Room.database` —— 要真实 SQLite
4. `android.(graphics|view|widget|content|util|icu|os|text).` —— 要平台图形/控件/文本/ICU
5. `androidx.(test|annotation|appcompat|recyclerview|core|fragment)` —— 要 AndroidX 运行时

**只判测试文件不够时，还要看被测类**：`LunarCalendarInstrumentedTest` 与 `LocationQrTest` 都是这一类（后者 `LocationQr.java:3-8` 用 `Bitmap/Canvas/Paint/Typeface` + `android.net.Uri`）。

### 1.1 可原样下沉 JVM 的清单：**0 条**

43 个文件里，**没有任何一个文件是不带决定性标记的**。逐文件标记见证据文件。这不是「懒得拆」，是这批测试当初就是冲着「真实 View 树 / 真实库 / 真实平台服务」写的——它们要检出的正是 JVM 检不出的那一层（`findViewById` 拿不到节点、真实 SQLite 的外键行为、主题解析出来的实际颜色）。

## 5. 设备占用前置检查：被占用就停，标「待复验」

跑之前**必须**先看前台是谁。命令与判据：

```bash
adb -s de5090fb shell dumpsys activity activities | grep topResumed
```

- 输出里是 `com.bai.bookshelf.devtest/...` 或 `com.android.launcher/...` 或系统设置页 → 设备空闲，可以跑。
- 输出里是**别的 App**（例如用户的课表 `com.hutb.timetable/.ui.MainActivity`）→ **立即停**，不抢前台，把这一档标成「待复验」并写明原因，等用户说设备空了再跑。

本轮实际撞过两次：T13 的返回键断言第一次跑到一半，前台被课表 App 抢走；第二次（2026-11-13 16:53）前台被系统页 `com.android.settings/.Settings$UsbDetailsActivity` 反复抢回。两次都按约定停手标「待复验」——这条规则不是纸面上的。**这两次「待复验」后来已解除**：不是靠抢回前台，而是换成 §5.1 的 shell uid 跑法（测试自己起宿主，不依赖人手提前台），17:28 整类 `OK (2 tests)`。规则本身不变——真被别的 App 占了前台，仍然停。

### 5.1 本机 MIUI 会拦「应用 uid 起 Activity」——已绕开，有确定跑法（2026-11-13 实测）

`CheckInYearBackInstrumentedTest` 是**全套 182 条里唯一真启动 Activity 的文件**（2 条；`grep -rln "ActivityScenario\|startActivitySync\|executeShellCommand" app/src/androidTest/` 只命中它）。它一开始在本机连续挂死，根因已取证：

```
ActivityStarterImpl: MIUILOG- Permission Denied Activity :
  Intent { ... cmp=com.bai.bookshelf.devtest/com.bai.bookshelf.ui.debug.CheckInBackHostActivity }
  pkg : com.bai.bookshelf.devtest uid : 10277 tuid : 1000
```

MIUI 拦的是**应用 uid 从后台起 Activity**，有时直接拒、有时弹 `com.miui.securitycenter/com.miui.wakepath.ui.ConfirmStartActivity`（`android.app.action.CHECK_ALLOW_START_ACTIVITY`）等人点。而 `ActivityScenario.launch` **没有超时**，等不到 RESUMED 就永久挂住。

**关键区分：shell uid 不受这条限制。** 实测 `adb shell am start -n com.bai.bookshelf.devtest/…MainActivity` 稳定成功并能保持前台；而 `am start` 宿主当时被 `SecurityException: not exported from uid 10277` 拒——**只因为宿主声明的是 `exported="false"`，不是因为 MIUI**。

试错记录（前三种都不成立，第四种才是解）：

| 试法 | 结果 |
| --- | --- |
| 唤醒屏幕后立刻起 instrument | 仍被拒——屏幕亮不是判据 |
| shell `am start` 宿主助推 | `not exported from uid 10277`，宿主没 exported |
| 先 shell 把 `MainActivity` 提到前台，再让 `ActivityScenario.launch` 起宿主 | **时灵时不灵**：17:18 那次起来了（46s），17:19 / 17:23 两次又挂死。前台会被 MIUI 确认框 / Settings USB 页抢回，不可依赖 |
| **宿主改 `exported="true"`（仅 debug 清单）+ 测试用 `UiAutomation.executeShellCommand("am start …")` 起它** | **稳定成功**：整类 2 条 `OK (2 tests)` / `Time: 12.376`，连跑两轮逐轮读数一致 |

**最终跑法的三个要点**（都已落进代码，不需要人手提前台）：

1. `app/src/debug/AndroidManifest.xml` 里宿主 `exported="true"`。**仅 debug 源集，不进 release 包**；`ShareCardPreviewActivity` 本来就是 `exported="true"`，同一写法。
2. 测试用 `UiAutomation.executeShellCommand` 起宿主——那条命令以 **shell uid** 执行（同一个通道能跑 `pm grant`，那是 shell 才有的权限，可反推身份），绕开应用 uid 的限制。等 RESUMED 用 **带 20s 超时的 `CountDownLatch`**，起不来就明确报错，不再静默挂死。
3. 宿主 `onCreate` 加 `FLAG_KEEP_SCREEN_ON | FLAG_TURN_SCREEN_ON`。**屏幕一灭就走 `onSaveInstanceState`，随后 `commitNow` 抛 "Can not perform this action after onSaveInstanceState"**（本轮真踩到）。用窗口标志而不是改 `stay_on_while_plugged_in`：标志随窗口销毁，**没有系统设置需要还原**。

**对分级的影响**：smoke 方案乙的 28 条**全部不启 Activity**，本来就不受这条限制；现在连那 2 条启 Activity 的也有确定跑法了，**全套 182 条在本机都可跑**，不再有「待复验」的硬阻塞。

证据：`dist/verify/v5.9.5/i5-i6/t13-miui-denial-logcat.txt`（早期拒绝日志）、`t13-device-real-activity.txt`（最终 `OK (2 tests)` 原始输出）。

配套纪律（沿用既有约定，不新增）：

- 真机**仅 de5090fb**，只读验证；**禁 `pm clear`、禁改 prefs**；**不启动模拟器 / 虚拟机**。
- 测试改过的系统设置必须还原（`stay_on_while_plugged_in`、字体缩放、动画时长等）。注意坑：电池 `status: 5`（FULL）会让 `stay_on_while_plugged_in=7` 失效，屏幕照样灭。
- 只对合成样本点「开始」；正式包 `com.bai.bookshelf` 与测试包 `com.bai.bookshelf.devtest` 分开，仪器化只装/只跑 devtest。
- 长跑期间前台被抢 → 停 + 标待复验，不重试抢回。

两个本机实测的坑：

- **别用 `timeout N env VAR=1 adb …` 包一层**：Git Bash 下实测立刻退 0、没有任何输出，等于根本没跑（本轮踩过，白等一轮）。要限时在外层脚本里做。
- **屏幕灭了会让启 Activity 的测试失败**（不是挂住，是 `commitNow` 抛 "Can not perform this action after onSaveInstanceState"）。宿主已自带 `FLAG_KEEP_SCREEN_ON`；跑之前再 `adb shell input keyevent KEYCODE_WAKEUP` + `wm dismiss-keyguard` 兜住启动前的空窗即可，**不用改任何系统设置**。

启 Activity 的那 2 条（T13 / T14，§5.1 的确定跑法，不需要人手提前台）：

```bash

adb -s de5090fb shell wm dismiss-keyguard
adb -s de5090fb shell am instrument -w -e class \

# 实测 OK (2 tests) / Time: 12.376
```

全量 182 条：去掉 `-e class` 整段即可。`DbRepairInstrumentedTest` 会造约 26 MB 的 zip，是全量约 18 分钟的主要来源——**smoke 里含它，所以 smoke 实测 10 分 54 秒（§3.2），不是秒级**，别按「很快」排期。
