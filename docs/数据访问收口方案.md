### 3.2 可直接照抄的模板：`StatsComputer.Source`

`app/src/main/java/com/bai/bookshelf/stats/StatsComputer.java:48`：

```java
public interface Source {
    List<BookCopy> bookCopies();
    List<BorrowRecord> borrowRecords();
    List<CheckIn> checkIns();
    List<Category> categories();
    List<NoteImage> noteImages();
```

实测三条关键性质：

- `StatsComputer.java` 的 import 里**没有一个 `android.*`**（只有实体、`util/`、`java.util`）。
- 适配器 `DbStatsSource` 是 `StatsFragment:730` 的私有静态内部类，只持 `AppDatabase`，逐方法转调 DAO。
- JVM 单测 `app/src/test/java/com/bai/bookshelf/stats/StatsComputerTest.java:89` 用**匿名假 Source** 喂数据，不需要设备。

**这就是字典试点要复制的形状**，而且它已经被 630 条 JVM 单测中的一部分覆盖着，形态是验证过的。

### 3.3 实体本身不拖 Android 框架

六个字典实体（`Location` / `Tag` / `Category` / `SourceChannel` / `Publisher` / `Country`）的 import 只有 `androidx.room.{Entity,PrimaryKey,ColumnInfo}` 与 `java.io.Serializable`。`androidx.room:room-common:2.6.1` 的实际产物是 **`.jar` 而不是 `.aar`**（已在 Gradle 缓存中核实），所以这些注解在 JVM 上可用。

实证：现有 JVM 单测 `stats/StatsComputerTest`、`ui/shelf/ShelfQueryTest`、`util/LibraryStatsTest` **已经在直接引用这些实体**。接口草案用实体做返回类型，不会把 Android 依赖带进纯逻辑层。

## 4. 为什么选「字典读取」做试点

| 判据 | 字典读取 | 对比：`bookDao` |
| --- | --- | --- |
| 形态一致性 | 31 处读几乎全是 `getAll()` / `getByXxx()`，无拼接 SQL | 74 处混查询/写入/事务/统计 |
| 事务边界 | **无跨表事务**（写侧的 Propagator 已单独收口） | 大量 `runInTransaction` |
| 失败语义 | 已有明确定义：每项独立容错、退回空列表 | 各调用点自行其是 |
| 可测性 | 假 Source 即可覆盖全部 7 条失败路径 | 需要真实 SQLite |
| 影响面 | 19 文件、31 处，**只读**，不改写入路径 | 全应用 |
| 与既有先例的贴合度 | 与 `StatsComputer.Source` 同形 | 需要新形态 |

**额外收益**：EP-I4 的 T12 刚给 `ShelfDictionaries` 的 7 处 `catch` 补了 ASCII 日志，当时只能靠**真机注入失败 + logcat** 取证。收口后这 7 条失败路径可以用假 Source 在 JVM 上直接断言，取证成本从「占设备」降到「跑单测」。

## 5. 接口草案（纯 Java，不含 `android.*`）

### 5.1 读缝隙

```java
package com.bai.bookshelf.data.dict;

import com.bai.bookshelf.data.entity.BorrowRecord;
import com.bai.bookshelf.data.entity.Category;
import com.bai.bookshelf.data.entity.Location;
import com.bai.bookshelf.data.entity.SourceChannel;
import com.bai.bookshelf.data.entity.Tag;

import java.util.List;

/**
 * 书架第二段渲染要读的字典。纯读缝隙，形状照 stats/StatsComputer.Source。
 * 实现方负责线程与异常；本接口不约定失败时返回 null 还是空列表，
 * 由 DictionaryLoader 逐项兜（保持 ShelfDictionaries 现有语义）。
 */
public interface DictionarySource {

    List<Location> locations();

    List<Tag> tags();

    List<Category> categories();

    /** 失败时允许返回 null：调用方要保留旧值，语义与其它六项不同 */
    List<SourceChannel> channelRows();

    List<String> countries();

    List<String> channels();

    /** 不是字典，但与字典同一次查询取回；拆出去是后续步骤，试点不动 */
    List<BorrowRecord> openLoans();
}
```

### 5.2 失败日志缝隙（把 `android.util.Log` 挡在纯逻辑层外）


### 5.4 适配器（留在 ui 层，持库与线程）

`ui/shelf/ShelfDictionaries.java` 改成薄适配器，**对外签名一字不改**（`loadAsync(BookshelfApp, Callback)`、`Data`、`Callback` 全部保留，调用方零改动）：

```java
public static void loadAsync(BookshelfApp app, Callback callback) {
    app.io(() -> {
        DictionaryLoader.Data d = DictionaryLoader.load(
                new DbDictionarySource(app.db()),
                (tag, msg) -> Log.w(tag, msg));   // T12 的 7 条 ASCII 日志原样保留
        app.ui(() -> callback.onLoaded(toUiData(d)));
    });
}
```

### 5.5 两条不许破的契约

1. **线程与崩溃兜底必须继续走 `BookshelfApp.io()`**。`BookshelfApp:273` 的 `guard(Runnable)` 会把「数据库本身坏了」的异常路由到修复页（`DbRepair.markBroken` + `openDatabaseRepair`）。仓库层**自带线程池就会绕过这层兜底**，等于把 v5.8 修的闪退问题重新引入。所以 `DictionarySource` 的实现**不开线程**，只在调用方给的线程里同步读。
2. **`channelRows` 的 null 语义不许统一成空列表**。现状是「查询失败为 null，调用方保留旧值」，其余六项是「失败退空列表」。把它一并兜成空列表会让来源渠道在库坏时被静默清空，属于用户可见行为变更。
