## 1. 两个候选站点：各自的真实后果

### 站点 A：`listBackups:653`（卡片点名的那个）

```java
private static List<BackupFile> listBackups(Context ctx, Uri treeUri) {
    List<BackupFile> list = new ArrayList<>();
    try { /* DocumentsContract 查询子文档，筛 小书房备份_*.zip */ }
    catch (Exception ignored) {
        // 枚举失败按空列表处理
    }
    list.sort((x, y) -> x.name.compareTo(y.name));
    return list;
}
```

枚举失败 → 空列表，两个消费端各自的后果：

| 消费端 | 正常 | 枚举失败时 | 用户看到什么 |
|---|---|---|---|
| :566 规则 2 去重 | 读到上一份，校验和相同就 `return` 跳过 | `existing.isEmpty()` → **不去重，照写一份** |  nothing（多占一份空间） |
| :582 规则 3 轮换 | `while (all.size() > MAX_KEEP)` 删最旧 | 空列表 → 循环一次都不进 → **旧备份永不删** | nothing（SAF 文件夹无限堆积） |

`MAX_KEEP = 5`（:74）。

**关键**：`writeTree` 本身是**成功**的（`createAndWrite` 写进去了），所以调用方走的是
`markSafOk(ctx)`（:222 / :380），我的页显示 `mine_dir_ok` =「%1$s · 外部副本 %2$s」——
**界面说外部副本正常，而「只保留最近 5 份」这条承诺已经静默失效**。

按卡 6 自己的分级口径（「A 会让界面、报表或**安全网**说出假话」），这条够得上 A，
但假话是「外部副本正常」，不是「还没有备份」。

对照：**内部**轮换的同形失败已经留痕了——:485-487
```java

    Log.w(TAG, "旧备份删不掉，超出保留 " + MAX_KEEP + " 份的上限：" + all[0].getName());

```
而 SAF 侧 :587 是 `catch (Exception ignored) { break; }`，一声不吭（这条是卡 6 单独登记的 B 级）。
同一个 App 里两条同形路径，一条有日志一条没有。

**可测性**：`listBackups` 依赖 `Context.getContentResolver()` + `DocumentsContract`，
**JVM 测不了**，只能 androidTest（还得真有一个 SAF 树）。

### 站点 B：`listInternal:531`（「还没有备份」的真正来源）

```java
private static File[] listInternal(File dir) {
    File[] files = dir.listFiles((d, name) ->
            name.startsWith(BACKUP_PREFIX) && name.endsWith(BACKUP_EXT));
    if (files == null) {
        return new File[0];      // ← 目录读不出来，与「目录里真的一份都没有」同一个返回值
    }
    Arrays.sort(files, (x, y) -> x.getName().compareTo(y.getName()));
    return files;
}
```

`File.listFiles()` 返回 null 的条件是「路径不是目录」或「发生 I/O 错误」——
不是「目录为空」（目录为空返回长度 0 的数组）。**两种情况现在被压成同一个值。**

四个消费端：

| 消费端 | 空数组的含义 | null 被压成空数组后的后果 |
|---|---|---|
| :548 `listInternalBackups` → `MineDataActions:146` | 一份备份都没有 | 我的页显示**「还没有备份（点此立即备份）」**，而实际上可能躺着 5 份 |
| :548 → `MineDataActions:349` `showBackupFiles` | 同上 | :353 `files.isEmpty() && broken.isEmpty()` 成立 → 弹 `mine_files_empty_msg`：**「还没有备份文件」+「在应用内保留最近 5 份备份」**，用户以为备份全没了 |
| :548 → `BackupManager:425` `verifyInternal` | javadoc 明写「没有备份时为空列表」 | `MineDataActions:255` `list.isEmpty()` → 弹 `mine_verify_empty`「还没有备份文件」：**一份都没验，却看起来像验完了** |
| :472 / :483 / :489 `writeInternal` | 没有旧备份 | 去重失效（多写一份）+ 轮换失效（内部 backups/ 也堆积） |

**这条才是卡片想描述的那个形状**：降级值（0 份）恰好是一个看起来像真数据的结论，
而且它同时污染三个用户可见出口 + 一条安全网。

`listInternal(File)` 是**纯 java.io**，不碰 Context。
JVM 上用一个临时目录就能把三种情况全造出来：
正常目录 / 不存在的路径 / 指向一个普通文件（后两者 `listFiles()` 必返回 null）。
仓库里已有同族 JVM 测试的先例：`BackupArchiveTest` / `BackupStreamingTest` / `PreMigrationBackupCopyTest`。

**这四条语义已实测，不是凭记忆断言**（`tmp/ListFilesProbe.java`，JDK 21.0.2，
输出存 `dist/verify/v5.9.5/exception-audit/listfiles-probe.txt`）：
```
populated dir -> len=2      （目录里 3 个文件，筛选后 2 个，无关.txt 被排除）
empty dir     -> len=0      （非 null！「0 份」与「读失败」在返回值上本来就可区分）
missing path  -> null
regular file  -> null
  sorted: 小书房备份_20260101_000000.zip
  sorted: 小书房备份_20260102_030405.zip
```
即：`listFiles()` 自己**已经把两种情况分开了**，是 :531 那句 `return new File[0]`
主动把它们压成同一个值。所以 B-1 不是「新增一套失败语义」，而是**把已有的区分保住**。

## 2. 选项

### 问题一：第 1 条改哪个站点？

- **甲（推荐）：改站点 B `listInternal:531`。** 理由：它才是「假零 → 用户可见结论」的那条，
  一次修好三个可见出口 + 内部轮换；而且能上 JVM 断言，符合规格「优先 JVM」。
  站点 A 降级为第 2 条（或并入 B 级留痕轮）。
- **乙：严格按卡片改站点 A `listBackups:653`。** 理由：尊重原文顺序。
  代价：断言只能 androidTest，且修完「还没有备份」那个假零**依然存在**。
- **丙：A、B 都算第 1 条，一起改。** 代价：违反「逐条过目」，且两处降级值设计不同
  （A 是 List、B 是 File[]），混在一条里不好审。**不推荐。**

### 问题二：站点 B 怎么改？（三个选项，都不动业务分支）

共同前提：`listInternal` 的**成功路径逐字不变**（同样的筛选、同样的排序、同样返回 `File[]`）。
只把「读失败」从「0 份」里分出来。

#### 选项 B-1：null 作为可区分降级值（推荐）

```java
static File[] listInternal(File dir) {          // private → 包内可见，供 JVM 单测直接调
    File[] files = dir.listFiles(...);
    if (files == null) {
        return null;                            // 读失败，与「0 份」分开
    }
    Arrays.sort(...);
    return files;
}
```
四个消费端各自加一道 null 判：
- `listInternalBackups`（:547）：失败时**返回 null**（现在返回空 List）。
- `writeInternal`（:472 / :483 / :489）：`existing == null` 时跳过「内容没变」判断（与现在空数组的行为一致）；
  `all == null` 时不进轮换循环（与现在一致）+ 补一条 `Log.w`（与 :486 内部轮换同形）。
  **成功路径与失败路径的业务动作都不变**，只是失败不再被当成 0。
- `verifyInternal`（:425）：null 时不能返回空列表冒充「验完了」→ 见问题三。

影响面：`BackupManager` 内部 4 处 + `listInternalBackups` 的 3 个外部消费端
（`MineDataActions:144` / `MineDataActions:349` / `BackupManager:425`）。
`listInternalBackups` 是 public，改返回语义要同时改这 3 处，**没有遗漏点**（grep 已闭合）。

#### 选项 B-2：保留空数组，另加一个失败标记

`listInternal` 仍返回 `File[0]`，但把失败记在一个包内可见的静态标记 / 传出参数里。
- 优点：现有 4 个消费端一行不用改。
- 缺点：静态标记是**跨调用共享状态**，备份在后台线程跑、我的页在主线程读，
  标记会被下一次调用覆盖 → 界面可能读到上一次的失败态。要修就得带线程/时序，
  比 B-1 复杂且更容易假绿。**不推荐。**

#### 选项 B-3：只补日志，不改降级值

`if (files == null) { Log.w(TAG, "backups/ 目录读不出来，这次按 0 份处理"); return new File[0]; }`
- 优点：改动最小，一行；不碰任何消费端；不碰文案。
- 缺点：**假零照旧**——我的页仍然显示「还没有备份」，验证备份仍然返回空。
  这等于把 A 级当 B 级处理，与本轮 P1 的目标（「让降级值可区分」）不符。
- 适用：如果用户认为「内部目录读不出来」在现实中几乎不可能发生（应用私有目录，
  非 root 不可改），可以只做留痕。**这是一个合理的取舍，请明确裁决。**

### 问题三：站点 A 怎么改？（若问题一选乙或丙）

- **A-1**：`listBackups` 失败返回 null；`writeTree` 两处判 null。
  去重与轮换的**动作不变**（都是跳过），但轮换跳过时补 `Log.w`，与内部 :486 同形。
  进一步要让「外部副本正常」不再说假话，就得让 `writeTree` 在「写成功但枚举失败」时
  走 `markSafFail` 而不是 `markSafOk`——**这一步改了业务分支**（成功/失败的判定变了），
  超出「只改异常处理」的约束，需要用户单独批准。
- **A-2**：只补 `Log.w(TAG, ...)`，降级值不动。同 B-3 的取舍。

## 6. 附带发现（只报告，本轮未动）
